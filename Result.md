# Отчет о проведённом тестировании мобильного приложения
В ходе проведения тестирования мобильного приложения "Мобильный хоспис" осуществлено ручное и автоматизированное тестирование следующих экранов (страниц) приложения:
- Authorization
- Main
- News
- Control panel
- Filter news (вход с экрана News)
- Filter news (вход с экрана Control panel)
- Creating News
- Editing News
- Love is all
- верхняя панель навигации приложения (top bar/ navigation bar)

## Тест-кейсы
Составлено 129 тест-кейсов для проверки максимально возможного количества функциональностей приложения, юзабилити, безопасности и совместимости с устройством.
## Автоматизация тестирования
- Автоматизированы 47 тест-кейсов, модулирующих использование ключевых функциональностей приложения и критический путь пользователя.
- Неполное покрытие тестов автоматизацией объясняется сложностью автоматизации некоторых тестов при более быстрой и простой ручной проверке, отсутствием возможности взаимодействия с устройством средствами автоматизации при осущесвлении ряда действий, наличием схожих проверок, покрываемых другими автотестами.
- Разработка тестов осуществлена под API 29 для экономии ресурсов системы с последующей отладкой под API 36 в соответствии с условиями задания.
- Для целей тестирования в код приложения внедрена регистрация Idling Resource, добавлены соответствующие классы (app/src/main/java/ru/edu/qamid/ui/data):
    * SplashIdlingResource.java - для ожидания тестами прохождения приложением сплэш-экрана;
    * NetworkIdlingResource.java - для ожидания тестами завершения обращения приложения к сети;
    * IdlingInterceptor.java - перехватчик обращений приложения к сети;
    * NavigationIdlingResource.java - для ожидания тестами завершения перехода между экранами;
    * ToastIdlingResource.java - для работы со всплывающими Toast-сообщениями.
- Тест shouldReturnEmptyControlPanelWithNoStatusFilter() в классе FilterNewsTest.java при прогоне получает статус skipped. Логика данного теста основана на следующем поведении приложения при фильтрации новостей:
    * при снятом чек-боксе Not active в ленте остаются только активные новости, 
    * при снятом чек-боксе Active в ленте остаются только неактивные новости,
    * следовательно, при снятых обоих чек-боксах в ленте не должно оставаться новостей,
    * однако в связи с отсутствием документации по приложению неизвестно, какую логику при такой фильтрации заложили разработчики, поэтому тест, обнаруживая в отфильтрованной ленте новости в статусе Active и Not active перехватывает исключение как известное и получает статус skipped (пропущен).
- Для проверки верхней панели навигации приложения отдельный тестовый класс отсутствует, так как функциональность верхней панели широко эксплуатируется во всех других тестах.
- В проекте используется инструмент Allure Framework  для логгирования и формирования отчётов о тестировании (Allure Report). Отчёт в формате html-файла приложен к проекту, доступен по [ссылке](allure-report/index.html).
## Баг-репорты
По результатам тестирования составлены 5 баг-репортов:
- Записывается неверная дата на экране Control panel при создании новости
- Отсутствует ограничение количества символов в поле Title на экране Creating News при создании новости
- Отсутствует ограничение количества символов в поле Description на экране Creating News при создании новости
- Элементы UI визуально неразличимы либо сложно различимы на различных экранах приложения при активации "тёмной темы"
- Отсутствует страница "О приложении" и элементы UI для перехода на неё с других страниц приложения

Баг репорты доступны в разделе Issues в репозитории проекта на Githab по ссылке: https://github.com/cedric-ko/qamid-diploma/issues.
## Сработавшие риски
Отсутствие документации приложения. Неоднозначность понимания функциональностей приложения и логики поведения.
## Сравнения времени ручного и автоматизированного тестирования приложения
- Ручное тестирование, без учёта времени составления чек-листа и тест-кейсов, заняло порядка 15 часов.
- Автоматизированное UI-тестирование, без учёта времени написания кода, по усреднённым результатам 5 чистых прогонов заняло 16 минут.
## Затраченное время
- В соответствии с планом тестирования, на настройка окружения, разработка автотестов и их отладка должны были занять 50 ч/ч.
- Фактически затраченное время составило 84 ч/ч.
- Причины превышения запланированных сроков работ:
    * из-за требовательности к ресурсам и медленной работы эмулятора Android API 36 первоначальную работу по автоматизации тестирования пришлось выполнять под API 29 с последующей отладкой;
    * помимо прохождения тест-кейсов пришлось столкнуться с эмулированием поведения устройства и учётом этого поведения в тестах (сплэшскрин, обращение к сети, задержки навигации, медленная работа эмулятора);
    * отсутствие достаточного опыта в выполнении подобных проектов.
